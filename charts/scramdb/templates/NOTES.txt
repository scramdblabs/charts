1. Connect

   Every node serves the same consistent database, so any pod is a correct
   endpoint. In cluster, the Service load balances across all of them:

     postgresql://{{ .Values.auth.username }}@{{ $fullname }}.{{ $ns }}.svc.{{ .Values.clusterDomain }}:{{ .Values.service.ports.pgwire }}/{{ .Values.auth.database }}

   From your machine:

     kubectl port-forward --namespace {{ $ns }} svc/{{ $fullname }} {{ .Values.service.ports.pgwire }}:{{ .Values.service.ports.pgwire }}
     psql "host=127.0.0.1 port={{ .Values.service.ports.pgwire }} user={{ .Values.auth.username }} dbname={{ .Values.auth.database }}"

{{- if and .Values.auth.enabled (ne .Values.auth.seedMethod "random") }}

2. The superuser password

     kubectl get secret --namespace {{ $ns }} {{ include "scramdb.authSecretName" . }} \
       -o jsonpath="{.data.{{ .Values.auth.secretKeys.passwordKey }}}" | base64 -d

   Seeded once, at first boot, while the superuser had no credential. Rotating or
   deleting this Secret afterwards never resets a password you set with
   ALTER ROLE, and never locks anyone out.
{{- else if and .Values.auth.enabled (eq .Values.auth.seedMethod "random") }}

2. The superuser password

   auth.seedMethod=random: the engine generated one and logged it exactly once,
   at first boot. Nothing else knows it.

     kubectl logs --namespace {{ $ns }} {{ $fullname }}-0 | grep -i password
{{- end }}

4. Watch the cluster form

     kubectl get pods --namespace {{ $ns }} -l app.kubernetes.io/instance={{ .Release.Name }} -w
     kubectl logs --namespace {{ $ns }} {{ $fullname }}{{ if .Values.regions }}-{{ (index .Values.regions 0).name }}{{ end }}-0 | grep -E "cluster transport: bound|swim: member up"

   Then ask the cluster about itself:

     SELECT * FROM scram.nodes;
     SELECT * FROM scram.shards;
     SELECT * FROM scram.freshness;

   A NULL in those relations means not measured, never zero.

5. Scaling

   Adding a node needs no configuration change: a new pod discovers the formed
   cluster through DNS, joins as a non-voting member and is promoted after it
   catches up.

     helm upgrade {{ .Release.Name }} --namespace {{ $ns }} --reuse-values --set replicaCount=<N>

   Removing one is also safe: a terminating pod hands its bucket ownership and
   its voter seat back before it exits, inside terminationGracePeriodSeconds
   ({{ .Values.terminationGracePeriodSeconds }}s here). To drain a node explicitly first:

     ALTER CLUSTER DRAIN '<node-name>';

   Changing the replica count re-derives bootstrap_expect, so the pods roll once.
   That is real reconfiguration work, not a no-op, and it is why the derived value
   is worth the roll: a stale one would refuse to form the next time the cluster
   is bootstrapped from empty.
{{- end }}

6. Cluster TLS

   Every pod mounts the certificate in Secret {{ .Values.cluster.tls.existingSecret }}. It must carry
   these node names (a peer whose certificate lacks the name it announces is refused)
   and the pods' stable DNS names, never a pod's address:

     {{ include "scramdb.clusterTlsNames" . }}
     *.{{ include "scramdb.discoveryDomain" . }}

   From the ScramDB repository:

     scripts/cluster_tls_certs.sh ./cluster-tls --shared {{ $fullname }} \
       {{ include "scramdb.clusterTlsNames" . }} 'DNS:*.{{ include "scramdb.discoveryDomain" . }}'
     kubectl create secret generic {{ .Values.cluster.tls.existingSecret }} --namespace {{ $ns }} \
       --from-file={{ .Values.cluster.tls.certFilename }}=./cluster-tls/{{ $fullname }}.pem \
       --from-file={{ .Values.cluster.tls.keyFilename }}=./cluster-tls/{{ $fullname }}-key.pem \
       --from-file={{ .Values.cluster.tls.caFilename }}=./cluster-tls/ca.pem

   A pod added past these names needs the certificate made again, listing it, under
   the same CA (ca-key.pem stays off the cluster).
{{- end }}
